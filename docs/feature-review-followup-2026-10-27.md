# 第二次功能檢查（2026-10-27）

本輪為檢查與建議，沒有修改網站功能。以下改善尚待確認，不自動視為實作需求。

重新執行 `npm run check`：114 項測試、畫面渲染、三份 Excel 範本、Apps Script 模擬與正式建置通過。下列情境不在既有測試涵蓋範圍；使用本機資料與模擬 API 檢查，未對真實 Google 檔案寫入，也未完成手機或 PDF 瀏覽器實測。

## 1. 高優先：復原草稿可能覆蓋後來的雲端變更

位置：`frontend/src/components/CatalogEditor.tsx:85`、`:99`、`:198`；`frontend/src/data/drafts.ts`。

草稿保存全部欄位，但未保存編輯當時的資料版本。重新開啟時，舊草稿覆蓋目前資料，快照卻使用最新清單。儲存前即使有快照檢查，這時也無法辨識舊草稿內哪些欄位已落後。

以模擬 API 確認：草稿建立時目的地為「大阪」，草稿只更名；雲端之後改成「京都」。重新載入後以最新快照儲存舊草稿，程式仍送出目的地「大阪」，未觸發衝突。

建議：草稿保留原始欄位／版本，復原時比較原值、目前雲端值與草稿值。僅套用使用者改過且雲端未衝突的欄位；衝突欄位由使用者選擇。補上跨表單開啟／重新整理的測試。

## 2. 中優先：改回原值後，已撤回的草稿仍可能復原

位置：`frontend/src/components/CatalogEditor.tsx:121`。

暫存只在 dirty 為 true 時更新。使用者先改名稱，隨後改回原名稱，dirty 變為 false，暫存卻不會更新或清除。

已按目前暫存邏輯模擬確認：畫面回到「原旅程」，儲存區仍為「稍後已撤回的更名」。再次開啟可復原到使用者已撤回的內容。

建議：回到乾淨狀態時清除該草稿，或持續同步目前值；仍有已建檔進度時需保留相應資料，不能一起丟棄。

## 3. 中優先：只修改國家搜尋字串就會清空設定

位置：`frontend/src/components/CountrySearch.tsx:56`、`frontend/src/components/TripFileCreator.tsx:170`。

已選國家後，輸入框每次修改會先呼叫 `onSelect(null)`。父元件隨即清空幣別、時區與匯率，這時使用者可能尚未選定新國家，甚至只是修改搜尋字串。

建議：分開搜尋字串與已確認選項；選定新國家時才套用新設定與清空匯率。取消搜尋或失去焦點不應丟失原有設定；明確按清除時再定義是否只清除國家選取。

## 4. 中優先：公開讀取檢查對空白列的判斷不一致

位置：`frontend/src/components/CatalogEditor.tsx:148`。

表單檢查要求原始旅程設定資料恰好兩列，正式解析則會忽略空白列。已用同一份資料確認：設定列後多一空白列時，正式 `parseTrip` 接受資料，公開讀取檢查卻會回報 ID 不一致。

建議：共用設定解析器，先排除空白資料列並正規化欄位，再檢查 ID；將「是否可公開讀取」與「設定是否有效」分別呈現，避免用同一段文字混合兩種狀態。

## 5. 後續改善：衝突比較應顯示欄位差異

位置：`frontend/src/components/CatalogEditor.tsx` 的 conflict-preview。

目前最新清單直接以 JSON 陣列顯示。雖能保留草稿並讓使用者採用新基準，但手機上難以判讀哪個欄位由誰改過。

建議以「欄位／原值／目前雲端／草稿」表格呈現，只列有差異的欄位，與第一項版本比較整合；避免再新增一套獨立確認流程。

## 驗證待辦

- 儲存草稿被瀏覽器阻擋時，現有訊息仍承諾「草稿會保留」。建議提供是否成功暫存的狀態；本輪未在實際限制儲存的瀏覽器測試。
- 既有資料層覆蓋率不能代表互動測試完整。應優先加入上面四種回歸情境，再在可執行的瀏覽器環境驗證手機下拉選單、草稿流程與 PDF 日期範圍。
- 新下拉箭頭 CSS 已統一右側 12px 間距，程式檢查未看到同等優先度的新問題；實際 iOS／Android 呈現仍待確認。
